4//! Quorum properties: what a quorum of validator signatures buys us.
5//!
6//! Throughout this module, fix a [`Committee`] and write
7//!
8//! * `N` for [`Committee::total_votes`],
9//! * `q` for [`Committee::quorum_threshold`],
10//! * `f⁺` for [`Committee::validity_threshold`],
11//! * `w(S)` for the sum of [`Committee::weight`] over a set `S` of validators.
12//!
13//! These are the only results in the specification that reason about weights arithmetically.
14//! Everything above this module consumes them through [`CorrectValidatorInIntersection`],
15//! [`CorrectSignerCastItsVote`], [`CertificateCarriesCorrectVote`] and
16//! [`CorrectValidatorsFormQuorum`].
17//!
18//! [`Committee`]: linera_execution::committee::Committee
19//! [`Committee::total_votes`]: linera_execution::committee::Committee::total_votes
20//! [`Committee::quorum_threshold`]: linera_execution::committee::Committee::quorum_threshold
21//! [`Committee::validity_threshold`]: linera_execution::committee::Committee::validity_threshold
22//! [`Committee::weight`]: linera_execution::committee::Committee::weight
23
24use crate::manager::proof::model::{CorrectValidator, MaxByzantineWeight, UnforgeableSignatures};

26/// **Definition (Quorum).** A *quorum* of a committee is a set `S` of pairwise distinct
27/// committee members with `w(S) ≥ q`.
28///
29/// Note that this is a statement about *weight*, not cardinality: [`Committee::weight`] returns
30/// `0` for a non-member, so a set containing non-members is never helped by them.
31///
32/// [`Committee::weight`]: linera_execution::committee::Committee::weight
33pub trait Quorum {}
34
35/// **Lemma (Threshold arithmetic).** `f⁺ = ⌈N/3⌉` and `2·q ≥ N + f⁺`.
36///
37/// *Proof.* [`Committee::new`] computes `validity_threshold = total_votes.div_ceil(3)`, which is
38/// `⌈N/3⌉` by definition of `div_ceil`, and
39/// `quorum_threshold = (total_votes + validity_threshold).div_ceil(2)`, i.e.
40/// `q = ⌈(N + f⁺)/2⌉ ≥ (N + f⁺)/2`. Multiplying the second by two gives the claim.
41///
42/// Both fields are stored rather than recomputed on use, so the proof needs them to be
43/// trustworthy on a committee that arrived over the network. They are: the `Deserialize` impl
44/// for [`Committee`] recomputes both from the validator weights and rejects the committee unless
45/// they agree with the serialized values (`CommitteeFull`'s `TryFrom` in
46/// `linera_execution::committee`). Hence every [`Committee`] reaching consensus code satisfies
47/// the two identities above. ∎
48///
49/// [`Committee`]: linera_execution::committee::Committee
50/// [`Committee::new`]: linera_execution::committee::Committee::new
51pub trait ThresholdArithmetic {}
52
53/// **Lemma (Quorum intersection).** Any two quorums `S₁`, `S₂` of the same committee satisfy
54/// `w(S₁ ∩ S₂) ≥ f⁺`.
55///
56/// *Proof.* `S₁ ∪ S₂` is a set of committee members, so `w(S₁ ∪ S₂) ≤ N`. Weights are additive
57/// over disjoint sets, so inclusion–exclusion gives
58///
59/// ```text
60/// w(S₁ ∩ S₂) = w(S₁) + w(S₂) − w(S₁ ∪ S₂) ≥ q + q − N ≥ (N + f⁺) − N = f⁺,
61/// ```
62///
63/// where the first inequality is [`Quorum`] applied to `S₁` and `S₂`, and the second is
64/// [`ThresholdArithmetic`]. ∎
65pub trait Intersection: ThresholdArithmetic {}
66
67/// **Lemma (A correct validator lies in every quorum intersection).** Any two quorums of the
68/// same committee share at least one correct validator.
69///
70/// *Proof.* By [`Intersection`] the intersection has weight at least `f⁺`. By
71/// [`MaxByzantineWeight`] the total weight of faulty validators is at most `f⁺ − 1 < f⁺`, so the
72/// intersection cannot consist of faulty validators alone. ∎
73pub trait CorrectValidatorInIntersection: Intersection + MaxByzantineWeight {}
74
75/// **Lemma (A valid certificate embeds a quorum).** If a certificate `c` verifies against a
76/// committee, then the signers of `c.signatures` form a [`Quorum`] of that committee.
77///
78/// *Proof.* There are two verification entry points, and both funnel into the crate-private
79/// helper `check_signatures`: [`LiteCertificate::check`], which the two block certificate types
80/// delegate to, and [`GenericCertificate::check`], which is what a
81/// [`TimeoutCertificate`] — a type alias for `GenericCertificate<Timeout>` — resolves to. Each
82/// builds the same [`SignedVotePayload`] and passes it with `c.signatures` to that helper, which
83/// (1) rejects a repeated signer with
84/// [`ChainError::CertificateValidatorReuse`], establishing pairwise distinctness; (2) rejects any
85/// signer whose [`Committee::weight`] is `0` with [`ChainError::InvalidSigner`], establishing
86/// committee membership; and (3) accumulates the signers' weights and rejects a total below
87/// [`Committee::quorum_threshold`] with [`ChainError::CertificateRequiresQuorum`], establishing
88/// `w(S) ≥ q`. Those three are precisely [`Quorum`]. The accumulation cannot overflow: step (1)
89/// establishes distinctness before step (3) adds, so the total is bounded by the committee's own
90/// `total_votes`, which [`Committee::new`] rejects on overflow. ∎
91///
92/// The signatures themselves are [`CertificateSignaturesVerify`].
93///
94/// [`LiteCertificate::check`]: crate::types::LiteCertificate::check
95/// [`GenericCertificate::check`]: crate::types::GenericCertificate::check
96/// [`TimeoutCertificate`]: crate::types::TimeoutCertificate
97/// [`SignedVotePayload`]: super::objects::SignedVotePayload
98/// [`Committee::new`]: linera_execution::committee::Committee::new
99/// [`ChainError::CertificateValidatorReuse`]: crate::ChainError::CertificateValidatorReuse
100/// [`ChainError::InvalidSigner`]: crate::ChainError::InvalidSigner
101/// [`ChainError::CertificateRequiresQuorum`]: crate::ChainError::CertificateRequiresQuorum
102/// [`Committee::weight`]: linera_execution::committee::Committee::weight
103/// [`Committee::quorum_threshold`]: linera_execution::committee::Committee::quorum_threshold
104pub trait CertificateEmbedsQuorum {}
105
106/// **Lemma (Every signature on a valid certificate verifies).** If a certificate `c` verifies
107/// against a committee — through either entry point named in [`CertificateEmbedsQuorum`] — then
108/// *each individual* signer of `c.signatures` holds a signature that verifies over the single
109/// [`SignedVotePayload`]
110///
111/// ```text
112/// (c.value.value_hash, c.round, c.value.kind, c.unlocking_round, c.first_round,
113///  c.justification_commitment)
114/// ```
115///
116/// *Proof.* Both entry points construct exactly that
117/// [`VoteValue`](crate::data_types::VoteValue) and pass it, with `c.signatures`, to
118/// `check_signatures`, whose final step calls `ValidatorSignature::verify_batch` and propagates
119/// any failure. For [`ValidatorSignature`] — an alias of `Secp256k1Signature` — that function is
120/// a loop of individual verifications returning on the first failure:
121///
122/// ```text
123/// for (author, signature) in votes {
124///     signature.verify_inner::<T>(prehash, *author)?;
125/// }
126/// ```
127///
128/// so acceptance of the whole is acceptance of each. ∎
129///
130/// **This is a property of the signature scheme, not of `check_signatures`.** The inference "the
131/// batch verified, therefore this particular signature verified" is a tautology only for a loop.
132/// `Ed25519Signature::verify_batch` — present in the crate, and marked unused in consensus — is a
133/// genuine batch scheme that differs in two ways:
134///
135/// * its soundness is *probabilistic*: it draws a random 128-bit scalar per signature and checks
136///   one aggregate equation, so an invalid signature survives with negligible but nonzero
137///   probability;
138/// * it does not accept the same set as single verification. `VerifyingKey::verify_strict`
139///   rejects small-order components explicitly and the batch path does not, and `ed25519-dalek`'s
140///   own documentation describes a malleability under which a mutated signature passes the batch
141///   though it "will not pass single signature verification".
142///
143/// Switching [`ValidatorSignature`] to such a scheme would leave
144/// [`CertificateCarriesCorrectVote`] standing — it needs only that *some* signature was produced
145/// by a correct validator — while silently invalidating this lemma and everything pointwise built
146/// on it. [`ConflictCompleteness`] is the sharp end: it extracts signatures out of certificates
147/// and re-verifies them *individually* through [`EquivocationProof::check`], so a batch/single
148/// divergence would make [`extract_equivocations`] emit proofs that verification rejects,
149/// breaking accountability completeness exactly where it is needed.
150///
151/// [`LiteCertificate::check`]: crate::types::LiteCertificate::check
152/// [`SignedVotePayload`]: super::objects::SignedVotePayload
153/// [`ValidatorSignature`]: linera_base::crypto::ValidatorSignature
154/// [`ConflictCompleteness`]: crate::justification::proof::ConflictCompleteness
155/// [`EquivocationProof::check`]: crate::justification::EquivocationProof::check
156/// [`extract_equivocations`]: crate::justification::extract_equivocations
157pub trait CertificateSignaturesVerify {}
158
159/// **Lemma (A correct signer of a valid certificate cast its vote).** If a certificate `c` is
160/// valid for a committee and a *correct* validator `v` is among its signers, then `v` itself cast
161/// a vote with `c`'s exact signed payload.
162///
163/// The validator is identified by other means — in practice by
164/// [`CorrectValidatorInIntersection`]. [`CertificateCarriesCorrectVote`] is the existential form.
165///
166/// *Proof.* By [`CertificateSignaturesVerify`], `v`'s signature verifies over `c`'s payload. By
167/// [`UnforgeableSignatures`] no party without `v`'s secret key produces a signature that verifies
168/// for `v`, so `v` produced it. By [`CorrectValidator`], a correct validator's signatures are
169/// produced only by this code driven through its public entry points, so producing that signature
170/// means casting that vote. ∎
171///
172/// Note what this does *not* need: no [`MaxByzantineWeight`], no [`ThresholdArithmetic`], no
173/// [`Quorum`]. The hypothesis already hands us the validator, so none of the weight machinery is
174/// involved — which is why this form, unlike the existential one, is available to
175/// [`crate::justification::proof`], where the fault bound is assumed *not* to hold.
176pub trait CorrectSignerCastItsVote:
177    CertificateSignaturesVerify + UnforgeableSignatures + CorrectValidator
178{
179}
180
181/// **Lemma (Every valid certificate carries a correct validator's vote).** For every
182/// certificate valid for its committee there is at least one *correct* validator that itself cast
183/// a vote with that certificate's exact signed payload.
184///
185/// This turns "a certificate exists" into "a correct validator executed the code path that
186/// produces this vote", and thereby lets the local implementation properties of
187/// [`crate::manager::proof::voting`] constrain what certificates can exist at all. An argument
188/// about a *particular* validator needs [`CorrectSignerCastItsVote`].
189///
190/// *Proof.* By [`CertificateEmbedsQuorum`] the signers form a quorum, of weight at least `q`. By
191/// [`ThresholdArithmetic`], `q ≥ (N + f⁺)/2 ≥ f⁺`, using `N ≥ f⁺ = ⌈N/3⌉`. By
192/// [`MaxByzantineWeight`] faulty validators hold at most `f⁺ − 1`, so some signer is correct.
193/// Apply [`CorrectSignerCastItsVote`] to it. ∎
194pub trait CertificateCarriesCorrectVote:
195    CorrectSignerCastItsVote + CertificateEmbedsQuorum + ThresholdArithmetic + MaxByzantineWeight
196{
197}

199/// **Lemma (The correct validators alone form a quorum).** The set of all correct validators of
200/// a committee is a [`Quorum`].
201///
202/// This is the availability counterpart of [`Intersection`]: it is what lets a correct proposer
203/// collect a certificate without any cooperation from faulty validators, and so it is a
204/// dependency of every progress result rather than of any safety result.
205///
206/// *Proof.* By [`MaxByzantineWeight`] the correct validators hold weight at least `N − f⁺ + 1`,
207/// so it suffices to show `N − f⁺ + 1 ≥ q`. Write `N = 3k + i` with `i ∈ {0, 1, 2}`; by
208/// [`ThresholdArithmetic`], `f⁺ = ⌈N/3⌉`.
209///
210/// ```text
211/// i = 0:  f⁺ = k,      q = ⌈(4k)/2⌉     = 2k,     N − f⁺ + 1 = 2k + 1 ≥ q.
212/// i = 1:  f⁺ = k + 1,  q = ⌈(4k+2)/2⌉   = 2k + 1, N − f⁺ + 1 = 2k + 1 ≥ q.
213/// i = 2:  f⁺ = k + 1,  q = ⌈(4k+3)/2⌉   = 2k + 2, N − f⁺ + 1 = 2k + 2 ≥ q.
214/// ```
215///
216/// In each case the correct validators reach the quorum threshold. ∎
217pub trait CorrectValidatorsFormQuorum: ThresholdArithmetic + MaxByzantineWeight {}

219/// **Remark (Where quorums are assembled, and why that is not load-bearing).** Certificates are
220/// built in two places, with different guarantees:
221///
222/// * [`SignatureAggregator::append`] performs the same three membership/distinctness/threshold
223///   checks as [`CertificateEmbedsQuorum`] incrementally, and verifies each signature as it is
224///   added, so a certificate it emits is valid by construction.
225/// * [`LiteCertificate::try_from_votes`] does **not** verify signatures, and instead requires
226///   its caller to have done so. Its one production caller,
227///   `linera_core::Client::communicate_chain_action`, verifies each vote against the responding
228///   validator's public key (in `linera_core::updater`) before aggregating, and groups incoming
229///   votes by their *full* signed payload — all six components of
230///   [`SignedVotePayload`](super::objects::SignedVotePayload) — so votes that disagree on the
231///   unlocking round, the first-round attestation or the justification commitment are never
232///   merged into one certificate.
233///
234/// Neither fact is load-bearing for safety. A certificate that a correct validator *acts on* is
235/// re-verified through [`LiteCertificate::check`] at every entry point that consumes one, so
236/// [`CertificateEmbedsQuorum`] applies to it however it was assembled; a malformed certificate
237/// that never passes `check` never influences a correct validator's state. The assembly path
238/// matters only for liveness, where a correct proposer needs its own certificates to be
239/// well-formed.
240///
241/// [`SignatureAggregator::append`]: crate::data_types::SignatureAggregator::append
242/// [`LiteCertificate::try_from_votes`]: crate::types::LiteCertificate::try_from_votes
243/// [`LiteCertificate::check`]: crate::types::LiteCertificate::check
244pub trait QuorumAssembly {}
